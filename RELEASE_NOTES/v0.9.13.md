Security release — **the token answer says what the credential is and how to keep it**. No manifest changes; every 0.9.12 manifest remains valid.

## The credential block

0.9.11 stripped the device-code token answer to the RFC members: the credential, its type, `tenant_id` and `auth_header`. Measured on a live service, a general-purpose assistant with no BEST client completed the device flow, received that bare key with nothing said about it, and printed it in the chat.

The token answer now carries the **credential block**:

- `note` (**required**) — the credential is a secret: stored in the client's configuration or credential store, never repeated in the conversation, and replaced if it ever appears there; a client that cannot store it says so instead of showing it.
- `endpoint` (**required**), `manifest`, `ready_check` — where the credential works, and a read that proves it.
- `mcp` — the connection as an MCP client's configuration (for the reference MCP server), the credential in its `env`.
- `http` — the surface for direct calls: the header with a **placeholder** for the credential, and the catalogue URLs.

The consumer chooses between configuring an MCP client and calling the surface directly. The credential appears only in `access_token` and in `mcp` — never in `note`, `http` or an example.

Manifest Discipline rule 5 is unchanged for descriptions and recipes; the token answer is where the service speaks to the consumer about the credential, because it is the only place the credential exists.

## Reference implementations

- `@behavioralstate/best-mcp` 2.5.1 keeps its behaviour — it stores the credential and redacts it — and drops the credential block's `mcp`, `http` and `note` from what the model sees: it is already the MCP client, and the choice is made.
