**Commands, queries and events are each the implementor's choice**, so a service with just one of them is BEST-compliant, as services that publish no events already were by best-validate. This release also adds one should on the manifest, takes out the `_best` TXT record, and builds the website's docs pages from `SPEC.md`. No schema changes shape: their only edits are descriptions. A 0.9.19 service stays compliant, unless a name it goes by serves no HTTPS and relies on the record (see Removed).

## Changed

- **Capability tiers.** Core is discovery alone. Commands, queries and events are the Primitives, and the implementor decides which to expose. A minimal BEST endpoint is a discovery manifest and one primitive. Workflows stay Extended. The Agent Navigation Guide recognises a service by any primitive.
- **How a client gets a command's results.** The results are events. How a client gets them is the implementor's decision: by polling a query the service defines or, where the service declares the events capability, from `GET /events` and its SSE stream.
- **The word is event.** The spec, the schemas' descriptions, the OpenAPI document and the examples say event, not domain event.
- **`send_command` and `source`.** `SPEC.md` said the caller must supply `source`. best-mcp has set it to `urn:best-mcp` when the caller supplies none since 2026-08-13, and the text now says so. On the wire `source` is always present.

## Added

- **Telling that a manifest changed.** A server **should** send an `ETag` and a `Cache-Control` other than `no-store` on `/.well-known/best`, so a consumer can tell that the manifest changed without reading it again. A `304` answering a conditional request is conformant. No manifest field is added: HTTP already carries this, and the manifest's `version` is the protocol version, which does not change with the document. best-validate 0.4.3 reports a response without them as a warning, and the run still passes.

## Removed

- **The `_best` TXT record** ([#213](https://github.com/behavioralstate/spec/issues/213)), defined since 0.9.10. Name resolution now has two steps: normalise the name, then fetch `https://{name}/.well-known/best`. A name that does not answer there does not resolve, and a name a service is publicly known by serves HTTPS, if only to redirect. No service checked publishes the record, neither best-mcp nor best-validate ever looked it up, and it let an unsigned DNS answer decide which host counts as the name. A service that published one can delete it.

## The website

A page in `specs/` that covers a section of `SPEC.md` no longer restates it: the build inserts the section's text, and the page holds only what the section does not say ([SDLC.md](../SDLC.md) section 2). A page naming a section that does not exist fails the build. Text that disagreed with `SPEC.md` went with the restatements, including the HTTP page's Multi-Tenant Routing section, which put `{tenantId}` in capability endpoints against Multi-Tenancy rules 2 and 4.

## The Internet-Draft

`draft-dinuzzo-best-protocol-02` stays what it is, a snapshot of 0.9.19. It still has events in its core and the `_best` record, and the next revision takes up this release.
