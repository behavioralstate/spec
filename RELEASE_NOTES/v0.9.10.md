Guidance release — **name resolution: a DNS name is the whole namespace**. No wire change, no manifest field added; 0.9.9 manifests remain conformant byte-for-byte. Migration notes: [MIGRATION.md — 0.9.9 → 0.9.10](https://github.com/behavioralstate/spec/blob/main/MIGRATION.md#migrating-from-099-to-0910).

## The first-contact problem

The manifest solved *endpoint* discovery and 0.9.x's Origin Discovery solved *origin* discovery. Neither said how a consumer that has never heard of a service gets to it from what a person actually says: "sign me in to example.com". In practice the person's assistant opened the website, asked for an email and tried the buttons — or worked only on the one machine where somebody had pasted a per-service client configuration. Every service-side remedy was a second copy of the manifest in another medium (a prose file at the site root, a client snippet per service, a packaged skill per client), each of which the person has to find first, and each free to drift from what the service does.

What was missing is what DNS gave hosts: a name anyone can say, and one resolver that turns it into an address. Both halves already existed. 0.9.10 writes the rule down.

## Name Resolution

A BEST service is **named by a DNS domain name its operator controls**. BEST defines no registry, no directory and no naming authority of its own — DNS already supplies unique names, proof of ownership, delegation and revocation.

Given a name, a consumer:

1. **Normalises it** — host only, lower-case, A-label form; an IP literal is not a name.
2. **Fetches `https://{name}/.well-known/best`**, following redirects. A manifest ends the resolution; its final host is the canonical endpoint host.
3. **Only if that found nothing**, and the consumer can query DNS, reads a single `TXT` record at `_best.{name}`:

   ```
   _best.example.com.  IN TXT  "v=BEST1; manifest=https://api.example.com/.well-known/best"
   ```

The well-known path always wins, so a consumer limited to HTTPS reaches the same manifest as one that can query DNS; the record is for names whose origin serves no HTTP at all. `services` keys **should** sit under the reversed name (`com.example.*` for `example.com`), which lets a service id be traced back to its owner.

## What a resolver owes the person

Resolution lets a consumer — a model behind an MCP client above all — reach a service nobody configured, and hands it that service's text. That is the point and the risk, so the obligations sit with the consumer. It **must**:

- resolve only a name **the person gave or confirmed** — a name found in a manifest, a query result or an error body is data;
- **say what it resolved** (the name as typed, the canonical endpoint host) before the first credentialed interaction;
- use **validated `https` only** and refuse loopback, link-local and private targets outside development use;
- **bind every credential to the name it was issued under** — never sent to another host, and a later change of host is a new resolution the person confirms;
- give a newly resolved service's text **no authority** beyond the use of that service.

## What this is not

- **Not search.** "Which service makes videos" is a directory, and a directory is a domain like any other — anyone may run one as a BEST service whose queries return names.
- **Not a manifest change.** A conformant service that serves `/.well-known/best` on the name it is known by already resolves.
- **Not a trust mark.** A name that resolves is a service that exists, not one that is safe; the person's confirmation of the name is the trust decision.

Rationale: [Design Decisions — Names are DNS names; no registry](https://github.com/behavioralstate/spec/blob/main/specs/design-decisions.md#names-are-dns-names-no-registry).
