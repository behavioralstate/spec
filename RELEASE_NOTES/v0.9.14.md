Security release — **the sign-in guidance**: the specification now says, in its own words, what a consumer does at each step of signing a person in, and every service carries those words verbatim. A manifest that declares `deviceAuthorizationUrl` adds `authentication.note`.

## What was measured

A general-purpose assistant with no BEST client, asked to sign a person in and pointed at a manifest, opened the manifest in a browser panel it drove and showed it to the person, said an approval page was open when none was, and wrote the credential into the commands it ran afterwards. 0.9.13's credential block reached it only at the last step, and said never to repeat the credential "in the conversation": a command, and its output, did not count.

## The sign-in guidance

Three texts, in SPEC.md ([Sign-in Guidance](../SPEC.md#sign-in-guidance)) and in `discovery.json` (`$defs/signInGuidance`):

- **Manifest text**, the `note` of an `authentication` block that declares `deviceAuthorizationUrl` (required): the manifest is for the agent, never shown to the person or opened in a browser; the form to post; the link the person opens in their own browser; never open it, sign in for them or ask for a password; poll; save the credential where only the person can read it, and never put it in a message, a command or any output.
- **Device text**, the device authorization answer's `note`: give the link and never open it; how to poll; save the credential, and read the rest of the answer without it.
- **Token text**, the start of the token answer's `note`: the credential is a secret, never repeated in a message, a command or any output, and read from where it is stored.

Verbatim, and the same on every service: a point an implementation can rephrase is a point it can drop, and a validator can check a text it knows.

## Other changes

- Agent Registration, step 3: the agent **must not** open the verification link itself or in a browser it controls.
- Manifest Discipline rule 5: the sign-in guidance is the one place a service speaks to the consumer about signing in and keeping the credential.
- Conformance item 11, required now, and a Security Requirement: the person approves in their own browser.

## Reference implementations

- `@behavioralstate/best-validate` 0.4.0 fails a manifest that declares `deviceAuthorizationUrl` without the manifest text and, with `--probe-registration`, a device answer without the device text.
- `@behavioralstate/best-mcp` 2.5.2 makes these requests itself, so `get_manifest` drops the guidance from what the model sees, and its own instruction says the person opens the link in their own browser.
