Additive release — the **`extensions`** object gives vendor-defined data one lawful home in the manifest. No removals; 0.9.6 manifests remain conformant. Migration notes: [MIGRATION.md — 0.9.6 → 0.9.7](https://github.com/behavioralstate/spec/blob/main/MIGRATION.md#migrating-from-096-to-097).

## Vendor data gets a lawful home — under a domain-first rule

The manifest schema is strictly closed (`additionalProperties: false` throughout) — a feature that keeps the core contract unambiguous, but one that left implementer-specific data with literally no legal position in the document: every extra key, useful or leftover, was equally non-conformant. The first casualty was real — a production deployment's leftover per-capability configuration failing validation with nowhere to migrate to.

0.9.7 adds one optional free-form **`extensions`** object in exactly two places — the manifest root (`best.extensions`) and each capability entry — and keeps everything else closed:

- Keys **should** be reverse-domain identifiers owned by the declarer (`com.acme.region`); `io.best.*` stays reserved for the spec.
- The core never interprets the contents; validators check only that the value is an object; consumers **must** ignore extensions they don't understand.
- No extension may be required in order to use a core capability.
- The manifest-hygiene rule applies unchanged: the root manifest is public, and an extension is not a private channel.

The governing rule is **domain-first**, and it is normative: anything dynamic, behavioral, or obtainable after authentication **must** be modeled as ordinary capability surface — a custom capability, a query, an event, a workflow (this is the same philosophy that removed registry, lifecycle, and memory from the core). `extensions` exists solely for **static, discovery-time declarations that must ride in the manifest document itself**: facts an unauthenticated indexer reads while classifying hosts, future manifest-integrity data that must cover the document, or a static annotation on a specific manifest element. Full reasoning: [design decisions — Manifest Extensions](https://github.com/behavioralstate/spec/blob/main/specs/design-decisions.md#manifest-extensions--one-escape-hatch-domain-first).

This also gives external standardization efforts (e.g. the IETF discovery work on attestation, capacity, and risk metadata) a compatibility path: such data enters as a namespaced extension and is promoted into the core only if a standard defines it.

- `@behavioralstate/best-validate` — schemas are synced from `protocol/v1/schemas` at build time; releases predating 0.9.7 fail a manifest carrying `extensions` (`additionalProperties: false`), so validate 0.9.7 servers with the matching validator release.
