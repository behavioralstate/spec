**No obligation waits for a later version.** Some of the specification's musts were dated to bind from a release that is not planned, since every release is a patch. The dates are taken out, and each must binds as the text states it. No schema changes shape: the OpenAPI document's only edit is a description. A service that does not meet one of these musts is not compliant with 0.9.21. best-validate still reports the ones it checks as warnings, and the run still passes.

## Changed

- **Dated obligations bind now.** These were dated to bind later:
  - Manifest Discipline rules 1–4;
  - the single entry, and what a site shows the person;
  - the errors of the device and token endpoints, per RFC 6749 §5.2;
  - the pseudo-tenant rule;
  - accepting `application/cloudevents+json` on `POST /commands`;
  - Conformance items 8 to 13;
  - the obligations in `specs/security.md`: refusing cleartext and the outbound rule, request records without credentials or query strings, a forwarded command's body, and the `413` and `429` answers.

  They bind now, as the musts the text already stated.
- **Conformance item 13** lists the pseudo-tenant rule and accepting `application/cloudevents+json` beside its other obligations. Only the paragraph that dated them had named them.
- **`MIGRATION.md`**'s 0.9.11 section calls its rules new requirements. The roadmap drops its enforcement row, and the design decisions drop the grace period.
- **How the specification is written** ([SDLC.md](../SDLC.md) section 2): a new must that an existing service could fail is listed in Conformance, and names no future version.

## best-validate 0.4.4

It checks the same rules, at the same levels: those it reported as warnings are still warnings, and a run with only warnings still passes. A warning no longer names a version, and its README lists every rule it reports as a warning.
