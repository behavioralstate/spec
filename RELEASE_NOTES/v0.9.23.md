**A command needs no background worker.** The Commands section said a service "validates, queues, and processes them asynchronously", and an implementer read that as requiring a queue with a worker behind it. It now says what was meant: asynchronous is what the caller sees, and how a service runs a command is its own. Nothing a conforming service does has to change.

## Changed

- **A service may process a command within the request.** [SPEC.md](../SPEC.md) (Commands) says that to queue a command is to record it durably, and that a service may then process it within the same request, before it answers `201`. The answer to `POST /commands` still never carries the result: the result is one or more events, read from a query the service defines or from `GET /events`, as before. This is a may, and adds no obligation.
