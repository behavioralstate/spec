Guidance release — **token exchange for header-constrained clients**, and rules for query-string credentials. No wire change; 0.9.7 manifests remain conformant byte-for-byte. Migration notes: [MIGRATION.md — 0.9.7 → 0.9.8](https://github.com/behavioralstate/spec/blob/main/MIGRATION.md#migrating-from-097-to-098).

## The headerless-client bootstrap problem

Not every legitimate client can set HTTP headers — URL-only integrations, webhook targets, embedded widgets, legacy tooling that accepts nothing but an endpoint address. Until now the manifest offered such clients exactly one road: `apiKey` with `in: "query"` — the long-lived key riding in the URL, where it leaks through request logs, proxies, `Referer` headers, and browser history.

0.9.8 defines the escalation path instead of inventing new machinery — the `authentication` block already had the slot:

1. **Headers** — `Authorization: Bearer` or the `apiKey` header, always preferred.
2. **Body exchange** — `tokenUrl` is now normatively an [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) token endpoint. Hosts serving header-constrained clients **SHOULD** accept the `client_credentials` grant — a form-encoded POST needing no custom headers — and return a **short-lived** `access_token` per §5.1.
3. **Query parameter, exchanged token only** — URL-only clients send the short-lived exchange output as `access_token` per [RFC 6750 §2.3](https://www.rfc-editor.org/rfc/rfc6750#section-2.3). Long-lived credentials **SHOULD NOT** be declared or accepted in a query string.

The invariant: **the long-lived credential is exchanged for a disposable one before it goes anywhere weaker than a header.**

Guard rails on the weak channel: servers **MUST NOT** log query-borne credential values, **SHOULD** send `Cache-Control: no-store` on those responses, and **SHOULD** issue query-eligible tokens with reduced scope — in particular, no [high-impact commands](https://github.com/behavioralstate/spec/blob/main/specs/security.md#high-impact-commands). And consistent with tenant isolation: tenant context binds to the exchanged credential itself — a tenant identifier in the exchange body is never authoritative, and a mismatch is rejected.

One-time login links (a single-use code minted from a dashboard, redeemed for a scoped token) are recognised as a valid implementation of the exchange for URL-only onboarding, but their issuance stays unstandardised — a host advertising one does so under a namespaced `extensions` key, per the domain-first rule.
